## 5. Recommended integration boundary

Use an **in-process, nonproduction producer-side adapter first**. It receives a `GovernedAssessmentResult` and its validated canonical input, explicitly bound synthetic snapshot and recommendation-instance identities, and synthetic assertion context. It checks one-to-one finding/recommendation/decision-version correspondence, complete collection and snapshot identity, then builds `LocalD8Input` and invokes the unchanged evaluator. Return local results only to tests. Existing governed validation, severity/risk/confidence rules, and the synthetic assertion validator are reused; no production handler, orchestration, package, handoff, EIP, or CEP call site changes. The adapter must reject unsupported context rather than manufacture an instance ID or client approval.

For real use, replace the synthetic authority boundary with a separately authorized producer-owned validation source and explicit recommendation-instance binding. Do not call the synthetic profile production authority, and do not treat an existing signed snapshot as authenticating separately supplied assertions.

## 7. Versioned contract strategy

**Recommend B: a separate, versioned D8 priority extension artifact**, initially internal and nonpublishable. The [v2 contract](../architecture/business-decision-package-contract-v2.md) has four recommendation fields; the [v3 contract](../architecture/business-decision-package-contract-v3.md) has exactly five, including `recommendationActionText`. `business-decision-package-v1` remains the legacy foundation. `business-decision-package-v2` is the governed default; v3 is explicitly selected. The `executive-runtime-response-v1` envelope and existing attestation profiles cover their respective exact package bytes and conclusion field order. An added priority field would change those frozen shapes and signatures.

The proposed artifact would reference an immutable producer snapshot digest and its verified package/attestation versions, carry its **own** contract and methodology/rule-table versions, and enumerate results by explicit recommendation instance. A future approved version must specify canonical bytes, issuer trust, artifact signature or equivalent integrity, replay/currentness checks, publication eligibility, and failure handling. No `v4` name, schema, signing profile, or production admission is presumed approved. Keep v2/v3 output and validation unchanged; support old and new artifacts side by side only through explicit version selection. Never silently strip or downgrade D8 data. A snapshot signature alone does not cover this extension.

## 8. Proposed result representation

For a future versioned artifact, propose a header with extension contract version, D8 methodology version, rule-table version, source snapshot identity/digest, underlying package contract version, and producer decision-version references. Each recommendation result should carry the governed finding ID and pair, exact recommendation instance ID and decision ID/version, logical outcome, optional `critical|high|medium|low` only when assigned, all winning peer IDs in sorted order, bounded reason code, and references to required approved evidence/provenance. Preserve confidence-gate status separately from priority. For PND, include evaluated D2/D3/D5 values (including explicit missing where an excluded rule does not need an assertion), excluded eligible rule IDs, `reviewRequired=true`, and a deterministic review correlation reference. Bind that reference to the real governed identity only after its design is approved; the local hash is not production review authority.

Internal evaluation may retain raw synthetic records, candidate/pending states, and full validation diagnostics. Publish only necessary identifiers, approved evidence/approval references, versions, outcome, and trace; omit evidence content and PII. `BLOCKED_REQUIRED_EVIDENCE`, `REJECTED_INVALID_ASSERTION`, and insufficient confidence are internal non-emitting outcomes unless a future contract explicitly permits a safe diagnostic projection. D7 `NO_FINDINGS_MONITOR` remains separate. PND is a review obligation, never a fifth level or completed assignment.

## 9. Fail-closed publication behavior

Validate complete governed input and exact snapshot/recommendation/decision versions before D8. Validate **all** supplied assertions, including those not needed by the winning rule; reject malformed, duplicate, conflicting, unauthorized, stale, withdrawn, superseded, or wrongly bound claims. Apply D7 and confidence gates, then three-valued rule-dependent evaluation. A potentially applicable higher rule pending evidence blocks lower emission. PND follows only when every eligible rule is conclusively false and retains its review trace. Unknown methodology or rule-table versions reject.

Distinguish three decisions: **evaluation outcome** (local D8 result), **publication eligibility** (future contract and authority gate), and **client review obligation** (PND or unresolved evidence). Do not publish a blocked or rejected state as a priority. Do not publish any D8 artifact if client authority/currentness is unverified, a required assertion is pending, identity or version binding fails, serialization fails, or artifact attestation/signature verification fails. PND publication itself needs an approved review workflow and contract representation; it cannot silently count as a completed assignment. Preserve existing v2/v3 handoff success or failure independently; do not let a D8 failure alter historical package bytes.

## 10. EIP/CEP compatibility

At the inspected EIP baseline, [snapshot compatibility](../../../executive-intelligence-platform/src/executive_intelligence_platform/snapshot_compatibility/compatibility.py) and [verified admission](../../../executive-intelligence-platform/src/executive_intelligence_platform/projection_delivery/verified_admission.py) validate exact governed shapes; [snapshot derivation](../../../executive-intelligence-platform/src/executive_intelligence_platform/snapshot_derivation/derivation.py) identifies governed package v2. A future D8 artifact therefore needs a separately approved version-aware consumer path and pass-through validation; existing admission cannot be assumed to accept it. Assessment Service alone evaluates priority. EIP must not recalculate it. CEP presents only an authorized projection; the AI Knowledge Assistant may explain approved results, not assign or override them. This plan changes no downstream repository or interface.
